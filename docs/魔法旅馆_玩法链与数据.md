# 魔法旅馆 — 玩法链与数据

> 本文记录 **当前工程已落地** 的玩法闭环、运行时数据、读写关系。  
> 需求目标看 [`魔法旅馆_Demo需求文档.md`](./魔法旅馆_Demo需求文档.md)。  
> 模块怎么拆看 [`魔法旅馆_技术架构.md`](./魔法旅馆_技术架构.md)。  
> 架构文档里的 Grid+A\*、伙伴、夜抉择、贝壳入箱等，**尚未全部实现**；以本文「已落地」为准。

阅读源码时先跟一局班次怎么转起来，再按三条玩法链往下钻。不要从 `navmesh/` 或单个 View 开始。

---

## 1. 怎么读源码

问一句：**这文件碰不碰 Node？**

- 不碰 → `domain/`、`fsm/`、纯函数（`DefaultAction`、`Recipe`）
- 碰 Node → `app/`（编排）或 `view/`（表现）

`ShiftController` 是阅读总入口：`start()` 装配，`update()` 推进，自己不写配方和寻路细节。

建议顺序：

1. `app/ShiftController.ts` — 一局有哪些系统、每帧谁在 tick
2. `app/DefaultAction.ts` + `app/InteractService.ts` — 点到台子后为什么是拿还是放
3. `app/Recipe.ts` + `app/ProcessorSystem.ts` — 灶炉怎么变成成品
4. `app/GuestLoop.ts` + `domain/Guest.ts` + `table/guests.json` — 客人闭环
5. `app/EventDirector.ts` + `app/incident/ThiefIncident.ts` + `table/events.json` — 突发事件
6. `view/PlayerView.ts` / `ThiefView.ts` / `ItemHoldView.ts` — 动画和持物，最后看

`navmesh/` 只在「路怎么走」时再读，和订单、配方无关。

## 3. 启动链

```
Battle.scene
  NavBakeStarter          烘导航网格
  PlayerBootstrap         等烘完 → new ShiftController.start()
  ShiftController.start
    读 items / recipes / guests / events
    StationRegistry.scan  按节点名认出灶炉 / 桌 / 放置台
    玩家：Actor + CommandFsm + PlayerView
    ProcessorSystem / GuestLoop / EventDirector
    ClickPicker → onClick
  ShiftController.update  每帧：寻路、指令 FSM、灶炉计时、客人、突发事件
```

关卡几何在 `LevelN.prefab`（台子、客人、Bat、HoldPoint）。关卡节奏在 JSON。

## 4. 三条玩法链

### 4.1 单击 → 走到台子 → 拿 / 放 / 煮 / 上菜

```
ClickPicker
  → ShiftController.onClick
       ├─ 这台上有停留的蝙蝠？
       │    EventDirector.scareAt(stationId)
       │    → 玩家 playAttack，蝙蝠空手飞回，再等 duration
       └─ CommandService.issue
            → CommandFsm 寻路
            → 到达 InteractService.arrive
                 → DefaultAction.resolveDefaultAction(手, 台, 客人要的菜)
                 → Take / Place / Stack / Serve / Bank / RefuseSwap / MoveOnly
```

`DefaultAction` 是纯函数 + 策略表。按 `StationType` 登记到 `STATION_RESOLVERS`。加新台子：写 `resolveXxx`，登记到表；漏登记编译报错。

| 手 | 台 | 结果（要点） |
| --- | --- | --- |
| 空 | 台上有货 | Take |
| 有货 | 台空 | Place（灶炉还要能查到配方） |
| 同 id | 台上同 id | Stack（上限 3） |
| 不同 id | 台上有货 | RefuseSwap |
| 客人要的成品 + 空桌 | Table | Serve |
| 桌上有金币 | Table | 空手 Take；手里有菜则 RefuseSwap（先拿走金币） |
| 手里金币 | Chest | Bank（tween 掉进箱子后销毁） |
| 灶炉正在 cooking | — | MoveOnly |

真正改数据的是 `InteractService`。改模型的是 `ItemHoldView`（HoldPoint 子节点）。  
玩家动画在 `PlayerView`：站着 idle，走路跑，取放投掷，驱赶攻击。

灶炉 Place 额外走 `ProcessorSystem.startFromHand`：

```
Recipe.findCookRecipe(hand.itemId)
  → station.slot = 1 份原料
  → cook.start(input, output, duration)
  → ProcessorView 进度条
  → tick 到 ready
  → slot 换成成品（burger → burgerbaked）
  → 灶炉 HoldPoint 换成品模型
```

### 4.2 客人：入座 → 等菜 → 上菜或超时离开

```
GuestLoop.start
  DiningHall.scanDining     Guest / Table / SeatPoint / LeavePoint / WaitPoint
  座位有空 → 寻路入座；坐满 → 去 WaitPoint 排队（间隔 WAIT_GAP）
  有人离席 → 队首补位入座，后面往前挪
  入座 → GuestOrderView 订单气泡
  Guest.tickWait（guests.json 的 waitTime）
       ├─ 桌上 slot 对得上 orderId → GuestFsm.serve
       │    桌上换成金币（Coin.prefab）→ 高兴 → 离店
       │    玩家 Take 金币 → 走到 TreasuerBox Bank
       └─ 超时 → GuestFsm.timeout → 生气 → 离店（不给金币）
```

客人要什么、等多久，只看 `guests.json` + `GuestCatalog`。  
节点名：`Guest0` / `Guest_1` / `RegularGuest` 都会归一成表里的 `guest` / `regularguest`。  
桌上有金币时不能上菜，必须先拿走。金币必须存进宝箱才算出手（`SHELL_BANKED`）。

### 4.3 突发事件：时间轴 + 一种事件一个类

```
EventDirector               按 events.json 的 delay 开事件
                            攻击型（thief）同时只 1 个；状态型（lock）可并行
  FACTORY[kind]             thief / lock / curse（诅咒仍占位）
  ThiefIncident
    warning（duration，默认 20s）
    → 飞向成品台 → hover
         ├─ 驱赶 / 没食物 → 回巢再等 duration
         └─ 偷走 → 回巢 Hit → 再等 duration
  LockIncident
    duration 预兆（0 则立刻）→ 未上锁灶炉 lockRemain = freezeTime（5s）
    Lock.prefab 挂 SCENE_UI 跟随灶炉，冷却到点销毁
    锁定期间不能拿放，烘培暂停
```

新事件：`events.json` 加一行 + 实现 `IIncident` + 登记 `FACTORY`。不要把事件分支写进 `ShiftController`。

## 5. 数据分两层

**配置（只读）** 开局进 `ConfigManager`，不放「手里有什么」。

| 表 | 内容 |
| --- | --- |
| `items.json` | id、叠加上限、显示名 |
| `recipes.json` | 灶炉 输入 → 输出 + 时长 |
| `guests.json` | 客人类型、耐心、`orderId`、订单预制体 |
| `events.json` | 事件 kind、delay、duration、stealCount、hoverTime、文案 |

当前配方：

- `burger` → `burgerbaked`（2s）
- `chickenleg` → `chickenlegbaked`（2s）

**运行时（会变）** 几乎全在 `domain/`。物品只存在两个地方：`Actor.hand` 和 `Station.slot`。

```
Actor                 玩家（以后伙伴也是一份 Actor）
  id
  hand                ItemStack | null
  speed

Station               StationRegistry 扫出来，每个台子一份
  id / type           place | cook | table | chest
  slot                ItemStack | null     宝箱不囤 slot，金币 tween 后销毁
  cook                CookProcess | null   仅 type === cook
  lockRemain          >0 则灶炉上锁，冷却到 0 解锁

ItemStack
  itemId              "burger" / "burgerbaked" / …
  count               1～ITEM_STACK_CAP（3）
  empty / sameAs / absorb / clone

CookProcess
  state               idle | cooking | ready
  elapsed / duration
  inputId / outputId
  progress            只读

Guest
  id
  state               entering | seated | reacting | leaving | gone
  orderId / waitTime / waited / urged
  tableId
  leaveReason         served | angry | null
  canAccept(itemId)
  tickWait(dt)        → urge | timeout | null

Command               这一次点了哪，不持久
  target              ground | self | place(stationId)
```

`StationBinding` **不是**玩法数据，只是查找表：`Station` ↔ 场景节点 ↔ HoldPoint ↔ InteractPos。

小偷没有独立 Domain。状态在 `ThiefIncident` 的 phase 里；偷东西改的仍是 `Station.slot` / `cook`。

## 6. InteractService 改哪些字段

`InteractService` 是「到达台子后改数据」的地方。不寻路、不写配方细节（灶炉委托 `ProcessorSystem`）。

| 动作 | 改的运行时数据 |
| --- | --- |
| **Take** | `actor.hand = station.slot`；`station.slot = null`；灶炉则 `cook.reset()` |
| **Place（普通台/桌）** | `station.slot = actor.hand`；`actor.hand = null` |
| **Place（灶炉）** | `startFromHand`：手上 `count -= 1`（空则 `hand = null`）；`slot = ItemStack(原料, 1)`；`cook.start(...)` |
| **Stack** | `station.slot.absorb(actor.hand)`；手上叠完则 `hand = null` |
| **Serve** | 先 Place 到桌，再 `GuestLoop.tryServe`：对得上则 `guest.state = reacting`，`leaveReason = served`，桌上 `slot = ItemStack(coin, 1)` |
| **Bank** | `actor.hand = null`；金币 tween 进宝箱后销毁 |
| **RefuseSwap / MoveOnly** | 不改数据 |

改完发：

- `ITEM_HELD_CHANGED`（actorId, hand）
- `STATION_SLOT_CHANGED`（stationId）

View 只听结果，不存第二份「手里有什么」。问「桌上有没有烤鸡腿」只看 `station.slot?.itemId`，不要扫节点。

灶炉计时不在 `InteractService`。`ProcessorSystem.tick` 把 `cook` 推到 `ready`，再把 `slot` 换成成品。

蝙蝠偷东西走 `ProcessorSystem.takeCooked`：`slot.count -= 1`，空则 `slot = null` 且 `cook.reset()`。

## 7. 数据链（谁写、谁读）

```
配置 JSON
  → ConfigManager
  → Recipe / GuestCatalog / EventCatalog   只读查询

玩家单击
  → CommandFsm 只改「在走路 / 已到达」
  → InteractService / ProcessorSystem / GuestLoop / ThiefIncident
       写 Actor.hand、Station.slot、CookProcess、Guest
  → EventBus
  → ItemHoldView / ProcessorView / GuestOrderView / PlayerView / ThiefView
```

| 数据 | 谁写 | 谁读 |
| --- | --- | --- |
| `Actor.hand` | InteractService、ProcessorSystem.startFromHand | DefaultAction、InteractService |
| `Station.slot` | InteractService、ProcessorSystem（ready / 偷） | DefaultAction、GuestLoop.tryServe、ThiefIncident |
| `CookProcess` | ProcessorSystem.startFromHand / tick；Take / 偷时 reset | DefaultAction、ProcessorView |
| `Guest.*` | GuestFsm、Guest.tickWait | GuestLoop、DefaultAction（wantedAt） |
| 突发事件 phase | ThiefIncident / CurseIncident | EventDirector、ShiftController.scareAt |

约定：

- Domain 不 `getChild`、不持有 Node。
- EventBus 传 `id`，不传 Node。
- 静态数不进 Domain；运行时血量/手里拿什么不进 JSON。

## 9. 数据结构为什么这样

1. **物品是栈，不是实体。** `ItemStack(itemId, count)` 一份，上限 3。三个汉堡模型只是 `count === 3` 的表现。
2. **位置用引用。** 物品要么在 `hand`，要么在 `slot`，`null` 就是空。Take/Place 挪引用，不从节点反推逻辑。
3. **台子类型决定有没有加工器。** 只有 `Cook` 带 `CookProcess`。客人状态机在 `Guest`，不塞进 `Station`。
4. **扩展靠登记表，不靠 ShiftController 里堆 if。** 新台子 → `STATION_RESOLVERS`；新事件 → `FACTORY`；新菜 → JSON（必要时补成品预制体）。
